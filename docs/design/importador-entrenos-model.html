#28 — Importador de entrenos · Excel/texto → prescripción tipada

El coach pega su Excel o su notación natural; la app lo tipa (cero texto libre), lo marca lo dudoso, y publica a la biblioteca de bloques o a la semana — con revisión obligatoria y aprendizaje de la notación de cada coach.

FASE DE DISEÑO · read-only · TODO coach-side web (sin iOS, sin lib/sync → no gateado por 1.0(3)) · mapeado contra el Excel REAL de Pablo (97 bloques) 2026-07-08

🛤️
No es greenfield — es el front de importación masiva sobre raíles que YA existen: (1) la GRAMÁTICA de la notación de Pablo ya está escrita (infra/scripts/parse_blocks_lib.ts: regexes exactas para 10/10/8/8/6, 65-80%, 5x3'30'', z2, 4x40''/20'', 12 rounds x 400m, km/h→ritmo + mapa de ~90 alias); (2) #33 acaba de construir los raíles IA→bloques tipados→editor→publicar (callPabloIaLlmJson con modelo por env nunca hardcoded, gate Zod, weekDayPartsToEditorBlocks); (3) el patrón de revisión por-campo (detected|review) de workout-vision.
🚪
El gate objetivo: nada entra sin pasar prescriptionSchema (.strict(), cero texto libre salvo note/tempo) Y con un exercise_id resuelto. Basura silenciosa rompería analíticas/reloj/IA — por eso NO es importación mágica: la revisión es obligatoria.
🧠
Lo net-new de verdad: el motor de parseo tipado (extraer la gramática a un módulo compartido testeado + fallback IA para lo denso), la resolución de ejercicios a escala, y el mapa de sinónimos por coach que aprende de las correcciones. La superficie de revisión = el editor de #33 pre-poblado y con lo dudoso marcado.

1 · El pipeline

pegar Excel/texto → PARSE tipado (gramática + IA) → resolver ejercicio (alias + sinónimos) → REVISIÓN (editor #33, dudoso marcado) → publicar (biblioteca / semana) → aprender sinónimos del coach

Cada elemento parseado es una propuesta con confianza por campo (detected|review, como workout-vision): lo detectado con seguridad va verde, lo dudoso ámbar, lo no-mapeado (ejercicio desconocido, WOD denso) rojo → el coach lo resuelve. Nada se guarda hasta confirmar y pasar el gate Zod.

2 · El objetivo tipado (lo que el parser DEBE producir)

El destino es la Prescription canónica que ya existe (shared/domain/prescription): medida × objetivo × modalidad, cero texto libre. El importador no inventa el modelo — lo rellena.

EjeValores tipados
scheme (formato)for_time · amrap · emom · tabata · death_by · intervals · steady · chipper · ladder · rounds · hyrox_sim · sets · warmup · cooldown
measure (trabajo)reps · distance(m) · duration(s) · calories
target (intensidad)percent_rm · kg · rpe · rir · bodyweight · pace(/km·/500m) · hr_zone(1-5) · hr_bpm · calories · watts — todos con rango (min/max)
sets[] (por serie){measure, target, rest_s, tempo} — pirámides/olas/bouts heterogéneos
estructurarounds · work_s · rest_s · total_s(cap) · start · increment
modalidadrun · row · ski · bike · strength · functional · core · mobility · other (intrínseca al ejercicio)

Bloque "mixto" (correr + wall balls) = varios items hermanos con el mismo block_position, cada uno su ejercicio + modalidad + prescripción. NO anidado. Único texto libre permitido: note (≤2000) y tempo ("3-1-1-0").

3 · El motor de parseo — híbrido, no IA sola

Gramática determinista exacta · gratis

  • Ya existe en parse_blocks_lib.ts: cubre la notación regular de Pablo (fuerza, ergo, series, zonas, core) EXACTO
  • Un regex no alucina un número — un LLM sí
  • Se extrae a un módulo compartido, testeado contra el Excel real
  • Sale como detected (alta confianza)

IA de apoyo para lo denso

  • callPabloIaLlmJson (modelo por env, el que elija Alex, nunca hardcoded; gate Zod)
  • Solo donde la gramática no llega: WODs/HYROX-sim densos, exercise-matching difuso, dialectos raros
  • Sale como review (el coach confirma) salvo que se auto-marque seguro

La gramática existente ya PUNTEA a needs_review los grupos 6/7/10 (WODs/sims/tapering) sin fabricar estructura — honestidad ya incorporada. El fallback IA los tipa como propuesta que el coach revisa. La primacía del motor es el Fork A.

4 · Resolución de ejercicios + sinónimos por coach (net-new)

El nombre del ejercicio en el texto ("SB lunge", "aperturas en polea") → exercise_id del catálogo. No hay columna de alias en exercises. Cascada: (1) mapa de alias global (~90, ya existe) → (2) match exacto/substring por nombre → (3) IA difusa → (4) si nada: la revisión pide al coach elegir/crear.

📚
El aprendizaje (el "aprende su notación"): cuando el coach resuelve un término no-mapeado, se escribe en un store nuevo coach_exercise_synonyms(coach_id, término_normalizado, exercise_id) (patrón de coach_exercise_overrides). El próximo import de ESE coach resuelve "SB lunge" solo. El mapa global de alias es el punto de partida; el per-coach es lo que se acumula.

5 · La revisión = el editor de #33 (reuso, no UI paralela)

El importador produce WeekDayPart[] tipados → weekDayPartsToEditorBlocks (client-safe, de #33) → el editor los muestra como bloques editables. La "pantalla de revisión con lo dudoso marcado" = ese editor, pre-poblado, con los items review/no-resueltos resaltados. El coach corrige ahí (ya conoce el editor) y publica con los seams que #33 ya usa.

⚠️
Único añadido al editor: mostrar la marca needs_review + razón por item (el dato ya existe en block_exercises.needs_review / el ParseResult.review_reasons de parse.ts) y el selector de ejercicio para los no-resueltos. No es una UI nueva; es un realce sobre el editor existente.

Biblioteca de bloques

  • Cada fila del Excel → un bloque tipado

9 · Forks — lo que decides tú / Alex

El objetivo (tipado correcto, cero texto libre, honestidad de la revisión, no fabricar) ya está decidido. Esto es lo subjetivo.

FORK A · motor de parseo primario

¿Gramática o IA primero?

A · gramática + IA fallback recomendado
Determinista primero (exacto/gratis en la notación regular de Pablo, ~70%), IA solo para lo denso/ambiguo. Un regex no alucina un número; el LLM sí. La gramática ya existe y ya cubre su notación.
B · IA primero + validación
IA tipa todo, la gramática/Zod valida. Más simple de escribir, pero riesgo de números alucinados en lo que la gramática clava.
C · IA sola
Todo por LLM. Descarta prior art exacto; más caro y menos fiable en dosis.
FORK B · granularidad de import v1

¿Qué se importa de una?

A · bloque + sesión recomendado
Fila Excel → bloque (biblioteca); texto de un día → sesión (editor de día). Cubre los 97 bloques + el editor de día que ya existe.
B · + semana/macrociclo
Pegar semanas/12-sem enteras. Más potente pero el editor de semana múltiple es más superficie; mejor fase 2.
C · solo bloque
Mínimo. Deja fuera el pegar-un-día, que es un caso real frecuente.
FORK C · superficie de revisión

¿Editor de #33 o pantalla propia?

A · reusar editor #33 recomendado
Pre-poblar el editor con lo importado + realzar lo dudoso. El coach ya lo conoce; cero UI paralela; publica con los seams existentes.
B · pantalla de import propia
Una vista dedicada de revisión masiva (tabla). Mejor para revisar MUCHAS filas de golpe, pero es UI nueva y duplica el editor.

Matiz: para importar 97 bloques de una, una tabla (B) escala mejor que abrir 97 en el editor. Posible híbrido: tabla de revisión masiva → editor por bloque al hacer clic. Lo dejo a tu criterio de UX.

FORK D · alcance del aprendizaje

¿Qué aprende el mapa por coach?

A · sinónimos de ejercicio recomendado
término→exercise_id por coach (donde más difieren los coaches). Alto valor, alcance acotado.
B · + alias de notación/formato
También abreviaturas de dosis/formato propias. La gramática ya es estable; menos retorno.
C · sin aprendizaje v1
Solo el mapa global. Cada import re-pregunta lo mismo — rompe la promesa "aprende su notación".
FORK E · líneas con doble objetivo (caso 6)

"Z2 pero no más de 6'/km" — zona + tope de ritmo

A · extender el modelo leve preferencia
Objetivo primario (hr_zone 2) + un tope/cap de ritmo tipado como segundo constraint. Más completo, pero toca el schema canónico de prescripción (cross-cutting).
B · primario + review
Tipar el objetivo primario y marcar el 2º como needs_review (el coach decide). No toca el schema; menos completo.

Es el único edge que roza "objetivo" (completitud del modelo). La FORMA del arreglo (extender vs review) sí es tuya porque el schema de prescripción se usa en todo el sistema.
